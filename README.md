# 기상특보 가능성

여러 기상 예보를 3시간마다 자동으로 모아 **지역별 기상특보 발효 가능성(%)과 예상 시간대**를 보여 주는 웹/앱(PWA)입니다.
비상근무 대비가 필요한 공직자·공공기관 직원을 위한 공개 서비스이며, 서버 비용 없이 GitHub Actions + GitHub Pages 만으로 돌아갑니다.

> **참고용입니다. 공식 특보·예비특보가 항상 우선합니다.**
> 실제 특보는 예보관이 관측과 영향을 종합해 발표하므로 계산 결과와 다를 수 있습니다.

- 대상 지역: **전국 226곳** — 기상청 특보구역(시·군, 세분 구역) 단위. 전남 22개 시·군과 보성(벌교)은 시·군청 위치로 다듬어 둠 — `config/regions.json`
- 대상 특보: 호우·강풍·대설·한파·폭염(주의보/경보/중대경보)·열대야 (태풍은 기상청 발표만 반영) — `config/thresholds.json`
- 비교 자료: 기상청 단기예보 + Open-Meteo 의 ECMWF · GFS · ICON · JMA — `config/settings.json`
- **실시간 자료**: 특보·예비특보, 지금 날씨(초단기실황), 앞으로 6시간(초단기예보)은 5분 간격으로 따로 받아 화면에 덮어 보여 주고,
  비구름 레이더(기상청 합성영상)는 화면이 직접 불러옵니다 — 아래 [실시간 자료](#실시간-자료)
- **철도 특보 지도**(`rail.html`): 전국 철도 노선·역 위에 지금 발효 중인 특보·예비특보 구역을 표시하고,
  전날까지의 코레일 공식 운행 기록으로 “특보 구간을 지난 열차가 얼마나 늦었나”를 집계합니다 — 아래 [철도 특보 지도](#철도-특보-지도)

## 구성

```
GitHub Actions (3시간마다)                                   GitHub Pages
┌─────────────────────────────────────────────┐            ┌──────────────────────┐
│ 수집  teukbo/sources/                        │            │ web/ (HTML·CSS·JS)   │
│   open_meteo.py    Open-Meteo 수치모델        │  배포       │  + data/latest.json  │
│   kma_forecast.py  기상청 단기예보            │ ─────────▶ │  + data/detail/*.json│
│   kma_warnings.py  기상청 특보·예비특보        │            │  + data/accuracy.json│
│ 계산  indicators → assess → scoring          │            └──────────────────────┘
│ 저장  data/history/날짜.json (커밋, 누적)      │               PWA: manifest + sw.js
│ 집계  data/accuracy.json (적중률)             │
└─────────────────────────────────────────────┘
```

| 폴더 | 내용 |
|---|---|
| `config/` | 지역, 특보 기준, 계산 파라미터 (코드 수정 없이 여기만 고치면 됩니다) |
| `teukbo/` | 수집·계산·저장 파이썬 패키지 (표준 라이브러리만 사용) |
| `tests/` | 단위 테스트 (`python3 -m unittest discover -s tests -t .`) |
| `web/` | 정적 웹 화면과 PWA 설정. 첫 화면 `index.html`(+`home.js`·`icons.js`·`records.js`)은 **지역 찾기 → 특보 종류 고르기 → 그 지역의 특보 가능성(작업 기준·날씨) → 지도 → 특보 기록** 을 보여 준다. 예전의 자세한 화면(`full.html` 모델 비교, `rail.html` 철도·레이더 지도, `analysis.html` 참고 자료)은 지우지 않고 남겨 두되 첫 화면에서 잇지 않는다 (`web/geo/` 는 지도용 지리 자료 — [web/geo/README.md](web/geo/README.md)) |
| `data/` | 누적 이력, 적중률, 열차 지연 집계 — [data/README.md](data/README.md) |
| `tools/` | 한 번만 쓰는 도구 (`build_geodata.py`: 지도용 지리 자료 만들기, `radar_calibrate.py`: 레이더 영상 위치 맞추기 — numpy·opencv 필요), `cloud_clock.gs`: 공개 사이트를 제때 갱신시키는 바깥 시계(구글 Apps Script) |
| `.github/workflows/` | `collect.yml`(3시간마다 수집·계산·배포), `live.yml`(5분마다 실시간 자료), `test.yml`(테스트) |

## 처음 설정하기

1. **이 브랜치를 `main` 에 합칩니다.** 예약 실행(cron)은 기본 브랜치에서만 동작합니다.
   GitHub Pages 무료 사용을 위해 저장소는 Public 이어야 합니다.
2. **인증키 발급** (없어도 Open-Meteo 만으로 계산은 되지만, 발효 특보·예비특보가 “확인 불가”로 나옵니다)
   - [공공데이터포털](https://www.data.go.kr) 에서 두 API 를 활용신청합니다(자동승인).
     - [기상청_단기예보 조회서비스](https://www.data.go.kr/data/15084084/openapi.do)
     - [기상청_기상특보 조회서비스](https://www.data.go.kr/data/15000415/openapi.do)
   - (권장) [기상청 API허브](https://apihub.kma.go.kr) 에도 가입해 **단기예보 조회**, **특보현황 조회**를 각각 활용신청합니다.
     공공데이터포털이 GitHub Actions(해외 IP)에서 막히거나 응답하지 않을 때 자동으로 이쪽을 씁니다.
3. **GitHub Secrets 등록** — 저장소 Settings → Secrets and variables → Actions → New repository secret

   | 이름 | 값 |
   |---|---|
   | `DATA_GO_KR_SERVICE_KEY` | 공공데이터포털 일반 인증키 (Decoding·Encoding 어느 쪽이든 됩니다) |
   | `KMA_APIHUB_KEY` | 기상청 API허브 인증키 (선택) |

   인증키는 코드·설정 파일에 쓰지 않습니다. 로그에도 `***` 로 가려집니다.
4. **GitHub Pages 켜기** — Settings → Pages → Build and deployment → Source: **GitHub Actions**
5. **첫 실행** — Actions 탭 → “수집·계산·배포” → Run workflow.
   끝나면 `https://<계정>.github.io/<저장소 이름>/` 에서 볼 수 있습니다. 실행 요약(Summary)에 출처별 성공 여부가 표시됩니다.

이후에는 기상청 단기예보 발표 직후(02:25, 05:25, … 23:25 KST 무렵)마다 자동으로 갱신됩니다 —
단, GitHub 의 예약 실행만으로는 제때 돌지 않습니다. 아래 **6단계(바깥 시계)** 까지 해 두어야 제시간에 갱신됩니다.

### 6. 공개 사이트를 제때 갱신하게 하기 — 바깥 시계 (필수에 가까움, 무료, 10분)

GitHub 의 예약 실행은 제시간을 보장하지 않습니다. 이 저장소에서 실제로 잰 값입니다.

| 기간 | 바깥 시계 | 5분마다여야 할 실시간 수집 | 3시간마다여야 할 수집·계산 |
|---|---|---|---|
| 2026-11-12 ~ 11-14 | 없음 (GitHub 예약만) | 4~7시간에 한 번 | 회차 여럿이 통째로 빠지고, 돈 회차도 1~3시간 늦음 |
| 2026-11-15 02:13 ~ 11-17 | 있음 (cron-job.org) | 5분 간격(최근 100회 가운데 99회가 바깥 시계의 신호, 모두 성공) | 17회차 연속으로 정해진 시각(25분)에 시작 |

그래서 **바깥에서 5분마다 ‘실행’ 신호를 보내 줄 시계**를 하나 둡니다. 자료 수집·계산·배포는 그대로 GitHub 이 하고, 시계는 신호만 보냅니다.

```
바깥 시계 (5분마다)  →  GitHub: live.yml 실행  →  실시간 자료(특보) 갱신
                                  └→ 3시간 주기의 수집·계산이 밀렸으면 collect.yml 을 시작시킴 (teukbo/schedule.py)
```

**① GitHub 토큰 만들기** (이 저장소의 ‘실행’만 시킬 수 있는 열쇠)

1. GitHub 에 로그인한 브라우저에서 아래 주소를 엽니다(이름·기한·권한이 미리 채워집니다).
   `https://github.com/settings/personal-access-tokens/new?name=teukbo-clock&expires_in=none&actions=write`
   (직접 찾아가려면: 프로필 사진 → **Settings** → **Developer settings** → **Personal access tokens** → **Fine-grained tokens** → **Generate new token**)
2. **Repository access**: **Only select repositories** → 이 저장소 하나만 선택
3. **Permissions** 에 **Actions: Read and write** 가 들어 있는지 확인(다른 권한은 주지 않습니다)
4. **Generate token** → 나온 값(`github_pat_…`)을 복사합니다. **이 화면을 벗어나면 다시 볼 수 없으니 곧바로 ②에 붙여 넣으세요.**
   놓쳤으면 같은 화면(Fine-grained tokens → 토큰 이름)에서 **Regenerate token** 으로 다시 뽑습니다(권한·저장소 선택은 유지, 이전 값은 무효).

**② 시계 고르기** — 둘 중 하나만 하면 됩니다.

**(가) cron-job.org — 휴대폰으로도 됩니다** (무료, 가입 필요. 토큰이 그 서비스에 저장됩니다)

1. <https://console.cron-job.org/signup> 에서 가입 → 메일 확인 → 로그인 → **CREATE CRONJOB**
2. **COMMON** 탭 — Title: 아무 이름, URL: `https://api.github.com/repos/<계정>/<저장소>/actions/workflows/live.yml/dispatches`, 주기: **Every 5 minutes**
3. **ADVANCED** 탭 (여기를 건너뛰면 실패합니다)
   - **Request method**: `POST` → 아래에 생기는 **Request body**: `{"ref":"main"}`
   - **Headers** 에 두 줄: `Authorization` = `Bearer` + 한 칸 + ①의 토큰, `Accept` = `application/vnd.github+json`
4. **TEST RUN** → `204 No Content`(또는 200)이면 성공 → **SAVE** (TEST RUN 만 하고 저장하지 않으면 적용되지 않습니다)

   | TEST RUN·기록(History)에 나오는 값 | 뜻 | 고칠 곳 |
   |---|---|---|
   | `404 Not Found` | GET 으로 나갔거나 토큰이 아예 없음, 또는 토큰에 이 저장소·Actions 권한이 없음 | Request method, Authorization 줄, ①의 2·3 |
   | `401 Unauthorized` | 토큰 글자가 틀림(다시 뽑기 전의 옛 값, 덜 붙은 값) | Authorization 값을 지우고 `Bearer` + 한 칸 + 새 토큰 |
   | `400` · `422` | 본문이 깨짐(따옴표가 바뀜) | Request body 를 복사해 다시 붙이기 |

   연달아 25번 넘게 실패하면 cron-job.org 가 작업을 스스로 끕니다(알림 메일은 **NOTIFICATIONS** 탭에서 켭니다).

**(나) 구글 Apps Script — PC 에서** (무료, 구글 계정만 있으면 됨. 토큰이 내 구글 계정에만 남습니다)

1. <https://script.google.com> → **새 프로젝트** → 편집기 내용을 지우고 [`tools/cloud_clock.gs`](tools/cloud_clock.gs) 내용을 붙여 넣고 저장
2. 왼쪽 톱니바퀴 **프로젝트 설정** → 맨 아래 **스크립트 속성** → **스크립트 속성 추가** → 속성 `GH_TOKEN`, 값에 ①의 토큰 → 저장
   (토큰은 코드에 적지 않습니다)
3. 왼쪽 시계 모양 **트리거** → **트리거 추가** → 함수 `tick` · **시간 기반** · **분 단위 타이머** · **5분마다** → 저장
4. 처음에는 구글이 권한을 묻습니다: 계정 선택 → “Google에서 확인하지 않은 앱” → **고급** → **(프로젝트 이름)(으)로 이동** → **허용**
   (구글 화면의 글자는 조금 다를 수 있습니다. 이 스크립트는 문법과 분기만 시험했고 구글 서버에서 돌려 보지는 못했습니다.)

**③ 확인** — 10분쯤 뒤 이 저장소의 **Actions** 탭에 “실시간 자료 (특보·지금 날씨)” 실행이 5분 간격으로 쌓이면 된 것입니다.

- 토큰은 이 저장소의 실행(Actions)만 다룰 수 있고 코드를 고칠 수 없습니다. 채팅·메일로 보내지 말고, 유출이 의심되면 ①의 화면에서 지우고 새로 만드세요.
  기한을 둔 토큰은 기한이 지나면 신호가 끊겨 다시 느려집니다 — 다시 뽑아 ②의 값만 바꾸면 됩니다.
- 5분마다 깨워도 호출 한도에는 걸리지 않습니다: 5분마다 도는 것은 가벼운 특보 확인(한 번에 기상청 조회 1~3번)뿐이고,
  무거운 수집·계산(한 번에 약 900번)은 그때마다 ‘정해진 시각이 지났는지’ 보고 3시간에 한 번만 시작합니다.
- 바깥 시계를 두지 않아도 사이트는 동작합니다. 다만 GitHub 예약이 올 때만(몇 시간에 한 번) 갱신되고, 계산이 4시간 넘게 오래되면 화면 맨 위에 경고가 뜹니다.

## 내 컴퓨터를 서버로 쓰기 (실시간)

파이썬만 설치되어 있으면 됩니다. 윈도우는 `start.bat`, 맥은 `start.command` 를 두 번 누르세요. **창을 열어 둔 동안** 그 컴퓨터가 서버 노릇을 합니다.

| 하는 일 | 주기 |
|---|---|
| 실시간 자료 — 특보·예비특보, 지금 날씨, 앞으로 6시간, 선로 강우(레이더) | **2분마다** (`config/settings.json` 의 `local.live_interval_seconds`) |
| 특보 가능성 예측 다시 계산 | 3시간마다 |
| 열차 운행 기록(전날까지) 채우기 + 분석용 집계 | 3시간마다 확인 |
| (선택) 공개 사이트 갱신 신호 | 실시간 5분마다 · 수집·배포 3시간마다 |

- 처음 한 번 공공데이터포털 인증키를 물어보고 `local_keys.txt` 에 저장합니다(이 컴퓨터에만 남고 커밋되지 않음).
- 브라우저로 `http://127.0.0.1:8000/` 을 엽니다. 화면은 1분마다 새 자료를 다시 읽습니다.
- 화면은 기본으로 **그 컴퓨터에서만** 열립니다. 같은 네트워크(같은 공유기·사무실 망)의 휴대폰·다른 PC에서도 보려면 `start-share.bat` 으로 실행하세요 — 창에 접속 주소가 나옵니다. 윈도우가 ‘액세스 허용’을 물으면 허용해야 합니다. 보기 전용이며 인증키 파일은 내보내지 않습니다.
- 컴퓨터가 절전에 들어가면 수집도 멈춥니다(화면에는 ‘갱신 지연’으로 표시). 계속 돌리려면 전원 설정에서 절전을 꺼 두세요.
- 인터넷·인증키 없이 화면만 보려면 `start.bat --demo` (가상 자료).

### 내 컴퓨터가 공개 사이트도 제때 갱신하게 하기 (선택)

위 ‘처음 설정하기 6단계(바깥 시계)’를 해 두었다면 필요 없습니다. 바깥 서비스 대신 **이 컴퓨터가 시계 노릇**을 하게 할 수도 있습니다(창을 열어 둔 동안만):
제때 GitHub 에 ‘실행’ 신호만 보내고, 자료 수집과 배포는 GitHub 이 그대로 합니다. GitHub 예약이 제대로 돌고 있으면 신호를 보내지 않습니다(두 번 돌리지 않음).

1. ‘처음 설정하기 6단계’의 **① GitHub 토큰 만들기**와 같은 방법으로 토큰을 만듭니다.
2. `local_keys.txt` 를 메모장으로 열어 `GITHUB_TRIGGER_TOKEN=` 뒤에 붙여 넣고 저장 → `start.bat` 을 다시 실행

## 설정 파일

### `config/regions.json` — 지역

전국 지역 목록은 `python3 tools/build_regions.py` 가 기상청 특보구역 코드표(`config/warning_zones.json`)와 구역 중심점(`web/geo/zones.json`)으로 만듭니다.
특보구역 하나가 지역 하나이고(예: 파주시동북부, 강릉시산지, 서울동남권), 손으로 다듬은 전남 시·군은 그대로 둡니다. 구역이 개편되면 도구를 다시 돌리세요(테스트가 파일과 도구의 결과가 같은지 확인합니다). 직접 항목을 넣거나 고쳐도 됩니다.

- 이름이 ‘산지’로 끝나는 구역에는 강풍·대설경보의 **산지 기준**을 적용합니다(`params` → `thresholds.json` 의 `region_param`).
- 열대야 기준은 제주 27℃·특별광역시 26℃·그 밖 25℃로 넣었습니다. 공식 기준의 ‘인구 50만 이상 도시·해안·도서 26℃’는 전남 외에는 아직 구분하지 못했습니다(그만큼 열대야 가능성이 높게 나올 수 있음 — 여름 전에 보완 필요).
- 전남 외 지역의 조회 지점은 시·군청이 아니라 **구역 중심점**입니다. 산지가 넓은 구역은 시가지보다 기온이 낮게 잡힐 수 있습니다.
- 전국 수집량: 해외 수치모델은 지점 50곳씩 6초 간격으로 나눠 받고(`settings.json` 의 `fetch`), 단기예보는 격자 6개씩 동시에 받습니다. 이력은 조용한 지역(모든 특보 가능성 0%·공식 특보 없음)의 모델별 극값을 생략해 용량을 줄입니다(등급·특보 기록은 모든 지역에 남음).

```json
{"id": "suncheon", "name": "순천시", "group": "jeonnam", "lat": 34.9507, "lon": 127.4872, "nx": 70, "ny": 70,
 "warning_zones": [{"code": "L1051200", "name": "순천"}],
 "params": {"tropical_night_min": 26}}
```

- `nx`, `ny`(단기예보 격자)는 `python3 -m teukbo.grid <위도> <경도>` 로 계산합니다.
- `warning_zones` 는 기상청 특보구역 코드·이름입니다(공공데이터포털 기상특보 조회서비스 첨부 「특보구역코드안내」).
  2026-05-31 구역 세분화로 한 시·군이 여러 구역으로 나뉜 곳(고흥북부/고흥남부 등)은 모두 적어 두었고,
  그중 한 곳이라도 특보가 있으면 그 시·군의 특보로 표시합니다. 여수의 거문도.초도, 신안의 흑산도.홍도도 포함됩니다.
- 다른 도를 추가할 때는 `zone_groups` 에 그 도의 코드·이름을 추가합니다(도 전체에 내려진 특보를 연결하는 데 사용).

기준값은 코드에 없고 모두 이 파일에서 읽습니다. 출처는 **기상법 시행령 [별표 1] (2026. 6. 30. 시행)** 과
[날씨누리 기상특보 발표기준](https://www.weather.go.kr/w/forecast/guide/standard.do)입니다(2026-11-12 확인).

| 특보 | 주의보 | 경보 |
|---|---|---|
| 호우 | 3시간 60mm 이상 또는 12시간 110mm 이상 | 3시간 90mm 이상 또는 12시간 180mm 이상 |
| 강풍(육상) | 풍속 14m/s 이상 또는 순간풍속 20m/s 이상 | 풍속 21m/s 이상 또는 순간풍속 26m/s 이상 |
| 대설 | 24시간 신적설 5cm 이상 | 24시간 신적설 20cm 이상 |
| 한파(10~4월) | 아침 최저기온이 전날보다 10℃ 이상 하강해 3℃ 이하(+평년보다 3℃ 낮음) 또는 -12℃ 이하 2일 이상 | 15℃ 이상 하강해 3℃ 이하(+평년보다 3℃ 낮음) 또는 -15℃ 이하 2일 이상 |
| 폭염 | 일 최고 체감온도 33℃ 이상 2일 이상 | 35℃ 이상 2일 이상 |
| 폭염중대경보(2026 신설) | — | 체감온도 35℃ 이상이 2일 이상 관측된 지역에서, 일 최고 체감온도 38℃ 이상 또는 일 최고기온 **39℃ 이상** |
| 열대야(2026 신설) | 폭염주의보 수준이 예상되면서 밤 최저기온이 지역별 기준(25℃, 해안·대도시 26℃) 이상 | — |

### `config/settings.json` — 계산·수집 파라미터

예측 범위(48시간), 비교할 모델 목록, 가능성 계산식의 가중치, 등급 구간, 재시도 횟수 등.

## 계산 방법 (1단계: 규칙 기반)

1. 자료(모델)마다 시간별 예측값으로 지표를 만듭니다: 3·12시간 누적 강수, 24시간 신적설, 시간별 풍속·순간풍속,
   일 최고 체감온도(기상청 여름철 체감온도 산출식), 밤·아침 최저기온 등.
2. 향후 48시간 안에서 특보별로
   - **도달률** = 자료별 최대 예측값 ÷ 기준값 (기온 지표와 ‘이하’ 기준은 `baseline` 으로 0% 지점을 옮겨 계산)
   - **초과 모델 비율** = 기준을 넘긴 자료 수 ÷ 전체 자료 수
   - **가능성(%)** = 50% × 초과 비율 + 20% × 점수(최대 도달률) + 30% × 점수(평균 도달률)
     — 점수는 도달률 50% 이하 0점, 100% 이상 만점, 사이는 비례. 식은 `teukbo/scoring.py` 의 `compute_probability()` 한 함수에 있습니다.
   - **예상 시간대** = 자료별로 기준을 처음 넘는 시각의 범위
3. 등급: 30% 미만 **낮음** · 30% 이상 **주의** · 60% 이상 **높음**.
   기상청 **예비특보**가 있으면 ‘높음’ 이상으로 올리고, 특보가 발표되어 있으면 **발효 중**으로 표시합니다.
4. **호우주의보는 주변까지 봅니다**(`teukbo/area.py`). 집중호우는 예보 모델이 비의 양과 위치를 조금씩 어긋나게 잡아서,
   그 지역 한 점의 예보가 기준(3시간 60mm · 12시간 110mm)에 닿기를 기다리면 대부분 놓칩니다(과거 검증: 하루 전 포착 71건 중 15건).
   그래서 반경 30km 안 지역들의 ‘도달률이 높은 2개 자료의 평균’ 가운데 가장 큰 값을 보고, 0.5 이상이면 **주의**(30%), 0.85 이상이면 **높음**(60%)이 되게 가능성을 올립니다.
   올리기만 하고(원래 식이 더 높으면 그대로), 경보 단계에는 쓰지 않습니다. 반경·자료 수·기준은 `config/thresholds.json` 의 `types.heavy_rain.area_score` 에 있습니다.
   기준은 과거 예보와 실제 특보를 맞춰 본 연구(`tools/rain_study.py`, 2026-09~11, 특보가 시작된 날 7일)로 정했습니다 —
   많이 잡는 대신 헛짚는 것도 늘고(‘주의’ 이상이 실제 특보로 이어진 것은 5번에 1번쯤), 가을 두 달의 자료라 다른 계절의 자료가 쌓이면 다시 맞춰야 합니다.

## 적중률

`data/history` 에 쌓인 기록으로 매 회차 다시 집계합니다(`data/accuracy.json`, 웹에 표시).

- **사전 포착률**: 실제 발효된 특보 가운데, 발효 12·24시간 전 시점에 ‘주의’ 이상이었던 비율
- **오경보율**: ‘주의’ 이상(또는 ‘높음’)으로 표시한 예측 가운데, 이후 48시간 안에 실제 특보가 없었던 비율

기상청 발표를 반영하기 전의 **계산 등급**으로 비교합니다(예비특보로 올린 등급을 쓰면 계산식의 성능을 알 수 없으므로).

## 실시간 자료

가능성 계산(수치모델 비교)은 예보가 새로 나오는 3시간 간격이면 충분하지만, **특보 발효·해제와 지금 날씨는 빨리 반영되어야** 합니다.
그래서 가벼운 수집을 따로 돌립니다.

| 무엇 | 출처 | 반영까지 |
|---|---|---|
| 특보·예비특보 발효/해제 | 기상청 기상특보 조회서비스 | 보통 5~10분 |
| 지금 날씨 (기온·1시간 강수량·풍속·습도) | 기상청 초단기실황 (매시 정시 기준, 10분마다 갱신) | 보통 5~15분 |
| 앞으로 6시간 (시간별) | 기상청 초단기예보 (매시 30분 발표) | 발표 뒤 20~30분 |
| 비구름 레이더 | 기상청 레이더 합성영상 (5분 간격) — 화면이 기상청에서 직접 불러와 특보·철도 지도에 겹쳐 그림 | 관측 뒤 5~10분 |
| **선로 강우 실황** | 기상청 레이더 합성영상을 서버가 직접 읽어 노선 위의 강수 강도를 계산 (`teukbo/radar.py`) | 관측 뒤 10~15분 |
| 실시간 열차 위치 | 한국철도공사 열차위치 화면을 그대로 끼워 보여 줌 | 코레일 화면 그대로 |

구조
```
live.yml (5분마다)  →  python3 -m teukbo.live  →  live.json  →  `live` 브랜치 (최신 한 벌만, 기록은 쌓지 않음)
화면(live.js)  →  https://raw.githubusercontent.com/<저장소>/live/live.json 을 2분마다 다시 읽어 latest.json 위에 덮어 그림
```

- **정확성 원칙**: 값마다 ‘확인 시각’을 따로 싣고, 화면은 30분(`config/settings.json` 의 `live.stale_after_minutes`)보다 오래된 실시간 값은 쓰지 않습니다.
  그때는 “실시간 갱신 지연”을 표시하고 3시간 주기 자료로 돌아갑니다. 조회에 실패하면 직전 값을 싣되 확인 시각은 바꾸지 않습니다(오래된 값을 새것처럼 보이지 않게).
- 화면의 등급 덮어쓰기(발효 중이면 ‘발효 중’, 예비특보면 최소 ‘높음’)는 서버 계산과 같은 규칙이며, 테스트가 두 결과가 같은지 확인합니다.
- **한계 — 엄밀한 실시간이 아닙니다.** GitHub 의 예약 실행은 5분이 가장 짧고 제시간을 보장하지 않으며(이 저장소에서는 몇 시간에 한 번만 온 날이 있음),
  파일 전달에도 최대 5분이 걸립니다. 5분 간격을 지키려면 ‘처음 설정하기 6단계(바깥 시계)’를 해 둡니다.
  1분 안팎의 반영과 안정성이 필요하면(실제 업무 판단에 쓰는 경우) 인증키를 보관하는 중계 서버(예: Cloudflare Workers 무료 요금제, 기관 내부 서버)에서
  `teukbo.live` 를 돌리고 `TEUKBO_LIVE_URL` 만 그 주소로 바꾸면 됩니다. 화면은 그대로 씁니다.
- 지금 날씨·6시간 예보(초단기실황·초단기예보)는 **꺼 두었습니다**(`settings.json` 의 `live.obs`·`live.fcst`). 첫 화면은 특보만 쓰고, 전국 226곳을 10~20분마다 받으면 하루 호출 한도(1만 건)를 넘기 때문입니다. 실시간 특보·예비특보는 그대로 받습니다.
- 코레일 화면은 권한을 줄인 틀(`iframe sandbox`) 안에 그대로 보여 주며, 그 안의 열차 자료를 읽거나 가공하지 않습니다(브라우저가 막습니다).

## 이 서비스만의 분석

남의 자료를 모아 보여 주는 데서 그치지 않고, 자료를 서로 엮어 다른 곳에 없는 결과를 만듭니다.

| 분석 | 엮는 자료 | 어디서 보나 |
|---|---|---|
| **특보 가능성** — 향후 48시간 특보 발효 가능성(%)과 예상 시간대 | 수치모델 5종 × 기상청 특보 기준 | 특보 전망 |
| **철도 구간 전망** — ‘주의’ 이상 지역을 지나는 노선과 시간대 | 특보 가능성 × 노선이 지나는 구역 | 특보 전망 |
| **선로 강우 실황** — 노선별로 지금 가장 센 비와 최근 1시간 추정 누적 | 기상청 레이더 영상(화소 색 → 강수 강도) × 선로 표본점 4,565개 | 지금 지도 |
| **노선별 특보 현황** — 지금 특보 구역을 지나는 노선·구역·역 | 실시간 특보 × 노선이 지나는 구역 | 지금 지도 |
| **특보 때 열차 지연·운행률** — 기간·특보·노선·열차 종류를 골라 다시 계산: 같은 열차의 평소 대비 지연 차이와 날짜 단위 오차 범위, 지연 분포, 특보가 걸린 날의 운행률과 평소 대비 운행 열차 수, 그날의 열차 찾기 | 코레일 운행 기록 × 특보 발표 이력 × 역의 특보구역 | 분석 |
| **예측 적중률** — 사전 포착률·오경보율 | 3시간마다 기록한 가능성 × 실제 특보 | 분석 |

### 과거 검증(백테스트)은 이렇게 합니다

`python3 -m teukbo.backtest` — 지난 예보로 가능성을 다시 계산해 실제 특보 기록과 맞춰 봅니다(`.github/workflows/backtest.yml` 이 매주 한 번, 또는 Actions 탭에서 직접 실행). 결과는 `data/backtest.json` 에 저장되어 첫 화면의 “이 가능성, 과거에 얼마나 맞았나”와 가능성 옆의 ‘과거 검증’ 한 줄로 나옵니다.

1. **실제 특보**: `data/rail/events/` 에 쌓아 둔 기상청 특보 발표·해제 이력(전국, 구역별 발효 구간).
2. **그때의 예보**: Open-Meteo Previous Runs API 의 ‘그 시각의 값을 하루 전·이틀 전에 예측한 값’(ECMWF·GFS·ICON·JMA).
3. **재현**: 6시간마다 그 시점으로 돌아가, 지금과 똑같은 계산식으로 지역별 가능성을 냅니다. 미래를 훔쳐보지 않게 재현 시점 기준 24시간까지는 하루 전 예측, 그 뒤는 이틀 전 예측만 씁니다(실제 서비스보다 오래된 예보 — 불리한 조건).
4. **맞춰 보기**: 실제 특보 한 건(한 지역에 특보가 새로 발효되거나 단계가 올라간 것 — 기상청 발표 기록의 발효 시각)마다, 발효 12·24시간 전의 재현에서 ‘주의’ 이상이었는지(사전 포착률)를 봅니다. 그리고 가능성 구간(0 / 1~29 / 30~59 / 60~100%)별로 48시간 안에 그 단계 이상의 특보가 실제로 시작된 비율을 냅니다 — ‘주의’·‘높음’이 맞은 비율도 이 표에서 나옵니다. 특보의 시작은 재현 시점이 아니라 발표 기록의 시각으로 세므로, 재현 시점 사이에 났다가 끝난 짧은 특보(호우특보에 많음)도 빠지지 않습니다.

한계: 기상청 단기예보는 과거분을 받을 수 없어 뺐고, 공식 예비특보로 등급을 올리는 부분도 넣지 않았습니다(계산식 자체의 성능). 표본은 서로 독립이 아니므로 특보가 있었던 날 수를 함께 적습니다. 화면의 ‘과거 검증’ 한 줄은 표본 30회 이상·특보가 있었던 날 3일 이상일 때만 나옵니다.

### 호우는 더 긴 기간으로도 확인합니다 (관측 기준)

특보 발표 기록은 60일 전까지만 조회되어 위의 과거 검증은 두 달 남짓입니다(가을뿐). 호우주의보는 여름 자료가 있어야 해서,
‘실제 결과’를 **기상청 관측(ASOS 일자료)** 으로 바꿔 2024-07 부터 다시 맞춰 봤습니다 — `tools/rain_longcheck.py`.

- 예보: `tools/cache/rain_<모델>_<기간>.json.gz` (Open-Meteo Previous Runs, 전국 226곳, 시간별 강수량의 ‘하루 전·이틀 전에 예측한 값’)
- 계산: 매일 0시에 그때까지의 예보로 호우주의보 가능성을 다시 계산 — 서비스와 같은 식(계산식 + 주변 30km 보정). 기상청 단기예보는 과거분이 없어 해외 모델 4개만.
- 실제: `tools/cache/asos_daily.json.gz` (94개 관측소 → 90개 지역). 그 0시부터 이틀(그날과 다음 날) 안에 관측소 일강수량이 80mm 이상이면 ‘큰비’.

결과(2024-07-01 ~ 2026-11-13, 864회 재현, 큰비 518건 · 큰비가 온 날 84일):

| | 지금의 계산(주변 30km 보정) | 보정 전 계산식 |
|---|---|---|
| 큰비를 전날 0시에 ‘주의’ 이상으로 표시 | 329/518 (64%) | 105/518 (20%) |
| ‘주의’ 이상 표시 뒤 이틀 안에 큰비 | 672/4,414 (15%) | 231/729 (32%) |
| ‘높음’ 표시 뒤 이틀 안에 큰비 | 327/1,115 (29%) | 46/87 (53%) |
| 0% 표시 뒤 이틀 안에 큰비 | 104/67,999 (0.2%) | 366/73,662 (0.5%) |

- 주변 보정의 기준은 2026-09~11 자료로 맞춘 것인데, **그 기간을 뺀 2024-07 ~ 2026-09-11 만으로도 전날 포착 63%(보정 전 20%)** 로 같았습니다 — 그 두 달에만 맞는 기준이 아니었습니다.
- 해마다 차이가 큽니다: 2024-07~2025-06 은 전날 포착 76%, 2025-07~2026-06 은 53%. 여름(6~9월) 65%, 그 밖의 달 52%.
- 문턱값을 바꿔도 공짜는 없습니다(포착을 올리면 헛짚는 횟수가 그만큼 늘어남). 그래서 기준은 그대로 두었습니다.
- **이 표는 특보 기준 표와 잣대가 다릅니다.** ‘특보가 발표됐는가’가 아니라 ‘관측소 한 점에 하루 80mm 이상 왔는가’를 봅니다.
  특보는 구역 어디든 3시간 60mm·12시간 110mm 에 닿을 것 같으면 나므로, 관측소 일강수량이 80mm 가 안 되어도 발표됩니다
  (특보 기록이 있는 2026-09~11 의 호우특보 28건 가운데 전후로 관측소 일강수량이 80mm 를 넘은 것은 3건, 중간값 43mm).
  시간자료가 있어도 ‘구역 대 한 점’의 차이는 남습니다.
- 다시 계산하기(네트워크 없이): `python3 tools/rain_longcheck.py --json data/rain_longcheck.json` → 첫 화면 검증 칸 아래쪽에 실립니다.
  관측 자료를 새로 받으려면 작업용 가지에서 Actions → “과거 검증” → regions 에 `4`.
- 공공데이터포털의 ASOS 는 **시간자료와 일자료가 따로 활용신청하는 별개 서비스**입니다. 여기서 쓰는 것은 일자료(`AsosDalyInfoService`)입니다.
  한쪽만 승인된 인증키로 다른 쪽을 부르면 “등록되지 않은 서비스키”가 옵니다.

### 지역별 기록과 체감온도는 이렇게 만듭니다

‘특보가 언제 발효됐고 그날 날씨가 어땠나’를 지역마다 한 파일(`data/records/<지역>.json`, 배포 전용)로 묶습니다.

- **특보가 발효된 날**: 열차 지연 집계가 받아 두는 특보 발표·해제 이력(`data/rail/events/`)을 지역의 특보구역으로 찾아, 그날 한순간이라도 발효 중이던 특보와 발효·해제 시각을 싣습니다. 이력을 받기 시작한 날(2026년 9월 중순)부터만 있습니다.
- **그날의 관측값**: 수집 뒤에 `python3 -m teukbo.obs` 가 기상청 관측소(ASOS) 일자료를 날마다 이어 받아 `data/obs/연-월.json` 에 쌓습니다(커밋, 지우지 않음). 전날 값은 오전 11시 뒤에 올라오므로 그 뒤 첫 회차에 지점마다 한 번씩만 부릅니다. 공공데이터포털의 「기상청_지상(종관, ASOS) **일자료** 조회서비스」 활용신청이 필요합니다(없으면 이 단계만 건너뜁니다).
- **어느 관측소인가**: 그 지역 안의 관측소, 없으면 가장 가까운 관측소(40km 안). 파일에 관측소 이름과 직선거리를 같이 싣습니다 — 지역 한가운데의 값이 아닙니다.
- **시간대별 값**: 수집 뒤에 `python3 -m teukbo.hourly` 가 기상청 **초단기실황**(지역 격자마다 짝지어 둔 대표 관측지점의 정시 값: 기온·습도·풍속·1시간 강수량·강수형태)을 정시마다 이어 받아 `data/hourly/날짜/시.json` 에 쌓습니다(커밋, 지우지 않음). 사이트를 조립할 때 지역별 한 달 파일(`data/hours/<지역>/<연-월>.json`, 배포 전용)로 묶고 시각마다 체감온도를 계산해 싣습니다 — 달력에서 날짜를 누르면 이 파일을 읽습니다.
  - 초단기실황은 **최근 23시간까지만 조회**됩니다(2026-11-26 실제 응답으로 확인). 수집이 하루 넘게 멈추면 그 사이의 시각은 빈 채로 남고, 수집을 시작하기 전의 날에는 시간별 값이 없습니다.
  - 가장 최근 정시는 다음 실행(3시간 뒤)에 받습니다(`hourly.skip_latest_hours`) — 진행 중인 시각의 값이 뒤에 바뀌는지 기상청 문서에 없어, 값이 굳은 뒤에 한 번만 받습니다. 그래서 달력의 ‘오늘’은 1~4시간 전 시각까지 보입니다.
  - 내 컴퓨터 모드(start.bat)는 시간별 실황을 받지 않습니다(`hourly.local`): 공개 사이트의 수집과 같은 인증키를 쓰면 하루 한도를 두 배로 씁니다. 저장소에 쌓인 값은 그대로 보여 줍니다.
  - 하루 약 5,400회(225격자 × 24시각)를 부릅니다. 같은 서비스의 하루 한도(개발계정 10,000건)를 단기예보 수집과 나눠 쓸 수도 있어 `hourly.daily_call_cap`(7,000)을 넘기지 않고, 한 번 실행에 쓰는 시간(`time_budget_seconds`)에도 상한을 둡니다. 실패해도 주 수집·배포는 계속합니다.
  - 값은 지역 격자의 대표 관측지점 것이라 **하루 값을 가져오는 관측소(ASOS)와 지점이 다릅니다.** 화면도 두 칸과 출처를 따로 적습니다.
- **그날의 체감온도 최저·최고는 시간별 값으로만** 구합니다(20시각 이상 있는 날만). 하루 값(최저기온·평균풍속)으로 어림하던 것은 뺐습니다 — 가장 추운 새벽에는 바람이 약한데 하루 평균 풍속을 넣어 실제보다 낮게 나왔습니다(보성군 2026-11-24: 어림값 -4.1℃, 정시별 실제 최저 -1.5℃).
- **예보의 체감온도**(`data/detail/<지역>.json` 의 `v:feel`)는 시간별 예보 값으로 계산합니다: 5~9월은 기상청 여름철 식(기온·습도), 그 밖의 달은 겨울철 식(기온·풍속 — 기온 10℃ 이하·풍속 4.8km/h 초과일 때만, 아니면 기온 그대로. 기상청 설명문은 “1.3m/s 이상”이지만 계산기와 날씨누리의 실제 표출은 4.8km/h 초과라 그쪽에 맞췄습니다). 달은 `config/settings.json` 의 `feel.summer_months`. 특보 가능성 계산에는 쓰지 않는 보여 주기용 값입니다(폭염특보 판단은 전처럼 `apparent`).
- 관련 설정은 `config/settings.json` 의 `records`(받기 시작하는 날, 전날 자료가 올라오는 시각, 관측소 거리 한도, 싣는 일수)입니다. 형식은 [data/README.md](data/README.md).

### 분석 화면(과거 자료 탐색)은 이렇게 만듭니다

화면은 위에서 아래로 한 방향으로 읽습니다: **① 조건 고르기 → ② 결과 요약 → ③ 날짜별 → ④ 특보 종류별 → ⑤ 지연 분포 → ⑥ 노선별 → ⑦ 특보가 있었던 날 → ⑧ 그날의 열차**. ①에서 고른 조건이 아래 모든 숫자와 그래프에 똑같이 적용되고, 구역마다 지금 조건을 다시 적어 둡니다.

- 서버가 날짜별 열차 목록(`data/rail/days/`)을 **날짜 × 노선 × 열차 종류 × 지나간 특보** 단위로 묶어 `data/rail/cube.json` 을 만듭니다(열차 수·지연 합·최대·지연 구간별 열차 수·평소 대비 합). 화면은 이 묶음 하나로 어떤 조건이든 다시 셉니다(`web/analysis-core.js`).
- **평소 대비** — 특보 구간을 지난 열차의 지연에서, 같은 열차번호가 특보 구간을 지나지 않은 날들의 평균 지연(그 열차의 ‘평소’)을 뺍니다. 같은 번호의 열차는 같은 구간을 같은 시각에 달리므로 노선·시간대·열차 종류가 저절로 맞춰집니다(요일대 월~목·금·토·일이 같은 운행이 3번 이상이면 그것만 사용).
- **오차 범위(95%)는 날짜를 단위로** 계산합니다. 같은 날의 열차는 함께 늦어지므로, 열차를 한 편씩 따로 센 것처럼 계산하면 범위가 실제보다 2~6배 좁게 나옵니다.
- **판정은 근거가 될 때만** — 평소와 견줄 수 있는 열차 30편 이상 · 특보일 8일 이상 · 하루에 40% 넘게 몰리지 않았을 때. 범위 전체가 ±1분 안이면 ‘차이 1분 미만’, 0보다 위면 ‘더 늦은 경향’, 아래면 ‘덜 늦은 경향’, 그 밖은 ‘판단 보류’. 특보일이 4일 미만이면 평균도 내보이지 않습니다.
- **가짜 특보 시험으로 확인** — 실제 기록에서 특보가 없던 날을 특보일로 꾸며 300번 계산했을 때 잘못 판정한 것은 1번(0.3%)이었고, 3분을 더한 자료는 모두 찾아냈습니다. 같은 시험을 합성 자료로 하는 테스트가 `tests/test_rail.py` 에 있습니다(평소 값을 중앙값으로 잡으면 31%를 잘못 판정해 평균을 씁니다).
- 화면의 계산과 서버의 계산(`teukbo/rail.py` 의 `matched_difference`)이 조건별로 같은 값을 내는지 테스트가 대조합니다.
- ‘보정 전’이라고 적힌 숫자(평균 종착 지연, 10분 이상 비율, 지연 분포)는 두 무리를 그대로 견준 것이라 노선·요일·시간대 구성의 차이가 섞여 있습니다.
- **운행률** = 운행계획에 있는 열차 가운데 운행 기록이 있는 열차의 비율. 계획 자료에는 노선이 없어 그날 **전체 열차 기준**으로만 내며, 특보가 걸린 날과 그 밖의 날을 나눠 함께 보여 줍니다. 한 편이라도 기록이 없으면 100.0% 로 반올림하지 않습니다.
- **운행 열차 수(평소 대비)** = 그날 운행 기록이 있는 열차 수 ÷ 같은 요일의 평소 열차 수(확정된 날들의 중앙값, 같은 요일이 3일 이상일 때). 운휴 열차가 계획 자료에서 아예 빠져 운행률이 100%로 보이는 날도 이 값이 줄어든 것으로 드러납니다. 실제 기록에서 요일별 열차 수는 ±2편 안에서 일정했습니다(2026년 10~11월). 명절·임시열차가 있는 날은 평소와 다를 수 있습니다.
- 특보 종류를 고르면, **다른 종류의 특보만 지난 열차**는 비교의 어느 쪽에도 넣지 않습니다(비교 기준을 깨끗하게 두려는 것).
- ⑧ 그날의 열차는 날짜를 골랐을 때만 그날 파일(`data/rail-days/날짜.json`)을 읽어, 열차번호·역·노선으로 찾을 수 있습니다.

### 선로 강우 실황은 이렇게 만듭니다

1. 기상청 레이더 합성영상(5분 간격, 635×620 PNG)을 받아 표준 라이브러리만으로 풉니다(OpenCV 결과와 화소 단위로 일치 확인).
2. 화소 색을 영상 범례의 24개 강수 강도 구간(mm/h)으로 되돌립니다. 범례 색이 달라지면 값을 읽지 않고 오류로 처리합니다.
3. 선로를 따라 약 1km 마다 찍어 둔 표본점(`config/rail_samples.json`)을 영상 좌표로 옮겨, 점마다 둘레 1화소(약 1.7km)에서 가장 센 값을 읽습니다.
4. 노선·특보구역별로 ‘지금 가장 센 곳’과 ‘최근 1시간 추정 누적’(구간 가운데 값 × 5분씩)을 냅니다.

우량계 관측이 아니라 **레이더 추정**이고 색 구간으로만 알 수 있으므로, 화면에는 구간(예: 5~6mm/h)과 ‘추정’을 함께 적습니다.

## 철도 특보 지도

`https://<주소>/rail.html` — 화면 위쪽 탭 “철도 지도”.

| 무엇 | 어떻게 |
|---|---|
| 지도 | 기상청 특보구역(육상 235곳) 경계 위에 철도 노선·역을 직접 그립니다(외부 지도 서비스·인증키 없음). 진한 채움 = 경보, 옅은 채움 = 주의보, 빗금 = 예비특보, 점무늬 = 이 서비스가 계산한 가능성(전남) |
| 비구름 레이더 | 같은 지도에 겹쳐 그립니다. 지도는 기상청 레이더 합성영상과 같은 도법(람베르트 정각원추, 표준위도 30°·60°, 기준점 126°E 38°N)으로 그리고, 영상의 축척·위치는 영상 속 해안선에 맞춰 구했습니다(`tools/radar_calibrate.py`, 98.5%가 1화소≈1.7km 이내). 영상에서 비구름 색만 남기고 바탕·해안선은 투명하게 처리합니다 |
| 지금의 특보 | 3시간마다 받는 기상청 특보 현황 전문을 전국 구역 코드로 풀어 `data/warnings.json` 으로 배포 |
| 열차의 실시간 위치 | 우리 지도에는 **표시하지 않습니다.** 공개된 실시간 위치 자료가 없고, 코레일 열차위치 화면의 내부 주소는 외부 프로그램의 접근을 허용하지 않습니다. 대신 코레일의 공식 열차위치 화면을 지도 아래에 그대로 끼워 보여 줍니다(특보 지도와 겹쳐 그리거나 분석에 쓰지는 못함) |
| 열차 지연 통계 | 한국철도공사 「열차운행정보」(공공데이터포털, **전날까지만 제공**)의 계획·실제 시각으로 종착 지연을 계산하고, 열차가 정차한 역의 특보구역에 그 시각 특보가 있었는지와 묶어 집계 (`teukbo/rail.py`, `teukbo/rail_run.py`) |

- 공공데이터포털에서 [한국철도공사_열차운행정보](https://www.data.go.kr/data/15125762/openapi.do)를 활용신청해야 합니다(같은 `DATA_GO_KR_SERVICE_KEY` 사용).
  신청하지 않았거나 실패해도 기상 수집·배포에는 영향이 없습니다(해당 단계만 건너뜀).
- 처음에는 과거 59일치를 한 번에 12일씩(최대 6분) 나누어 채웁니다. 며칠 지나면 모두 채워지고 이후에는 하루치씩 늘어납니다.
- 전날 기록은 다음 날 새벽~오전에 올라옵니다(자정 직후에는 아직 없음). 올라오는 도중에 받았을 수 있으므로
  그날이 끝나고 하루가 더 지나기 전까지는 실행 때마다 다시 받아 달라진 내용을 반영합니다(`final: false`).
- **통계의 뜻**: 특보와 지연이 같은 때 있었다는 것만 보여 줍니다. 사고·고장·선로 작업 등 다른 원인이 섞여 있으므로
  “특보 때문에 늦었다”는 뜻이 아닙니다. 정차역 기준이라 정차하지 않고 지나간 구역의 특보는 반영되지 않습니다.
- 열차 종류(KTX·무궁화 등)는 공식 자료에 없어 열차번호 대역으로 나눕니다(`config/settings.json` 의 `rail.train_classes`).
- 광역전철(수도권 전철 등)은 운행 기록에 없어 통계에 포함되지 않습니다.

## 운영하면서 알아 둘 점

- **GitHub 의 예약 실행은 제시간을 보장하지 않습니다**(한 시간 넘게 늦거나 아예 빠짐 — 이 저장소에서는 몇 시간에 한 번만 온 날이 있음).
  그래서 수집·계산이 시작되는 길을 세 겹으로 두었고, 어느 길로 오든 ‘정해진 시각(3시간 간격)이 지났는데 아직 그 회차를 돌리지 않았을 때’만
  실제로 수집합니다(`teukbo/schedule.py` — 같은 회차를 두 번 계산하지 않고, 때가 아니면 자료를 받지 않고 몇 초 만에 끝남).
  1. **바깥 시계**(처음 설정하기 6단계)가 5분마다 실시간 수집을 깨우고, 실시간 수집이 끝에서 ‘밀렸으면’ 수집·계산을 시작시킵니다. ← 제시간을 지키는 길
  2. 수집·계산 자체의 GitHub 예약(매시 25·55분) — 바깥 시계가 없거나 멈췄을 때의 대비
  3. 실시간 수집의 GitHub 예약(5분마다라고 적지만 실제로는 드물게 옴) — 올 때마다 1과 같은 확인을 합니다.
  그 회차가 실패하면 40분 간격(`local.trigger.collect_retry_minutes`)으로만 다시 시작시킵니다(무료 한도를 재시도로 써 버리지 않게).
  계산 주기를 3시간보다 크게 줄이기는 어렵습니다 — 기상청 단기예보가 3시간마다, 해외 수치모델이 6시간마다 새로 나오고,
  Open-Meteo 무료 한도(하루 10,000회)에서 전국 226곳 × 모델 4개는 한 번에 약 900회라 하루 11번이 상한입니다.
- **특보 종류 고르기**: 찾기 칸 아래의 줄(전체·호우·태풍·강풍·대설·한파·폭염·열대야)에서 종류를 고르면 가능성·지도 색·특보 기록이 모두 그 종류만 보여 줍니다.
  고른 종류는 다음에 열 때도 기억합니다. 단추의 점은 그 종류의 등급(‘주의’ 이상일 때만)입니다.
- **가능성은 ‘무슨 특보인지’부터**: 종류 그림과 특보 이름(예: 강풍주의보)을 크게 먼저 적고, 그 아래에 %·등급·막대(낮음·주의·높음 구간)와 예상 시간대를 적습니다.
  전에는 %만 크게 보여 비인지 바람인지 한눈에 알기 어려웠습니다. ‘전체’에서는 가장 눈여겨볼 종류가 머리에 오고 나머지 종류는 그 아래 한 줄씩(누르면 그 종류로).
- **작업 기준(폭염·한파)**: 고른 지역의 예보 체감온도·특보 가능성에 맞춰 법령과 고용노동부 지침의 단계를 보여 줍니다(의무/권고를 구별해 표시).
  수치·문구·근거는 모두 [`config/work_rules.json`](config/work_rules.json) 에 있고 화면 코드에는 없습니다 — 폭염 대책은 해마다 5월, 한파 대책은 11월에 새로 나오니 그때 이 파일의 내용과 `checked_at` 을 고치면 됩니다.
  ‘전체’를 볼 때는 제철인 기준만 접어서, 한파·폭염을 고르면 펼쳐서 보여 줍니다. 화면의 판정은 예보로 계산한 값이며, 법의 체감온도는 작업장소에서 잰 값입니다.
- **특보 기록(달력)**: 지도 아래에 고른 지역의 한 달 달력이 나옵니다 — 칸마다 날짜, 그날의 관측값(종류에 따라 최저기온·강수량·순간풍속 등), 특보가 발효됐던 날에는 단계 띠.
  날짜를 누르면 발효·해제 시각과 그날의 관측값, 그 아래에 **시간대별 체감온도·날씨**(체감 최저·최고와 그 시각, 24시간 띠, ‘이 날 시간별 표 복사’)를, ‘이 달 표 복사(엑셀용)’를 누르면 그 달의 표를 탭으로 나눈 글로 복사합니다(엑셀에 그대로 붙습니다).
  자료는 배포 때 만드는 `data/records/<지역>.json`(아래 ‘지역별 기록과 체감온도’)이고, 관측값은 가까운 기상청 관측소의 값이라 이름과 거리를 같이 적습니다.
- **움직임**: 지역이나 종류를 바꾼 첫 그림에서만 위에서부터 떠오르고, 숫자가 올라가고, 막대가 차오릅니다(몇 분마다 다시 그릴 때는 움직이지 않습니다). 종류 그림은 가능성의 머리에서만 조금씩 움직이고,
  바탕에는 비 오는 시간대에 빗줄기, 밤에 별이 옅게 깔립니다. 모두 자리·투명도만 바꾸는 가벼운 것이고, 기기의 ‘움직임 줄이기’ 설정을 켜면 멈춥니다(`style.css` 맨 아래 묶음).
- **? 단추(도움말)**: 제목 옆의 ?를 누르면 ‘등급과 특보 단계’가 뜹니다 — 이 화면의 등급(낮음·주의·높음·발효 중)이 무엇을 뜻하는지와 과거에 그 등급이 얼마나 맞았는지,
  기상청 특보 단계(예비특보 → 주의보 → 경보), 접어 둔 ‘특보 종류별 발표 기준’. 등급의 경계와 발표 기준 글은 화면 코드가 아니라 자료(`config/settings.json` 의 grades,
  `config/thresholds.json` 의 official_text)에서 읽습니다. 닫기 단추·바깥 누르기·Esc 로 닫습니다.
- **여는 화면(인트로)**: 첫 화면을 열면 로고의 게이지 눈금이 차오르며 바늘이 올라가고, 이어서 ‘기상특보 가능성’ 이름이 나타납니다(글은 이름 하나뿐, 4초 남짓).
  자료가 그려지면 걷힙니다(누르면 바로 걷힘).
  같은 탭에서 새로고침할 때는 건너뛰고, 자료를 못 받았을 때도 걷혀 안내 글이 보입니다. 스크립트가 돌지 않아도 6초 뒤 CSS 가 스스로 걷습니다.
  인트로가 떠 있는 동안에는 본문을 그리지 않고(자리만 잡아 둠) 걷히기 시작할 때 그립니다 — 가려진 채 그려지고 날씨 칸이 늘면서 밀린 지도가
  일부 휴대폰(삼성 인터넷)에서 위쪽이 빈 채로 남는 일이 있었습니다(누르면 돌아옴). 같은 까닭으로 칸의 배경 흐림(backdrop-filter)을 뺐고, 걷힌 뒤 지도 칸을 한 번 다시 그립니다.
- **첫 화면의 아래쪽은 접어 둡니다**: ‘이 가능성, 과거에 얼마나 맞았나’는 숫자 셋(하루 전에 잡아냄 · ‘주의’ 이상 맞음 · ‘높음’ 맞음)과 한 줄 설명만 보이고,
  구간별 표 · 특보 종류별 표 · 호우의 긴 기간 확인 · 방법과 한계는 눌러서 펼칩니다(펼친 칸은 화면이 다시 그려져도 유지). 바닥글도 한 줄 안내와 접는 칸입니다.
  휴대폰 기준 전국 화면 길이가 3.8화면 → 2.0화면으로 줄었습니다. 내용은 빼지 않았습니다.
- **계산이 늦어졌을 때 화면이 하는 일**: 계산이 4시간(`config/settings.json` 의 `stale_after_hours` — 주기 3시간 + 여유 1시간)보다 오래되면
  맨 위에 “자료가 N시간 전 것입니다” 경고를 띄웁니다. 첫 화면의 날씨 요약(지금 기온, 비 시작, 시간대별 줄)은 계산한 시각이 아니라
  **보는 시각**을 기준으로 다시 잡습니다 — 이미 지나간 시간대는 빼고 남은 예보만 보여 주며(비가 오는 시간대면 “지금 비 예보”),
  예보 기간이 모두 지났으면 날씨를 싣지 않습니다. 가능성(%) 자체는 다시 계산되기 전까지 그대로입니다.
- **Open-Meteo 호출 한도는 접속 IP 기준**(하루 10,000회 등)입니다. GitHub Actions 는 여러 사용자가 IP 를 함께 쓰므로
  내 사용량과 무관하게 `429` 가 날 수 있습니다. 그 회차는 받은 자료만으로 계산하고 화면에 빠진 모델을 표시합니다.
  모든 예측 자료를 못 받으면 실행을 실패 처리하고 이전 배포를 그대로 둡니다(화면에는 “자료가 N시간 전 것” 경고).
- **공공데이터포털은 GitHub Actions(미국 IP)에서 간헐적으로 연결 시간 초과**가 보고되어 있습니다.
  `KMA_APIHUB_KEY` 를 등록해 두면 실패 시 자동으로 API허브로 넘어갑니다. API허브는 API 마다 활용신청이 필요합니다.
- **Open-Meteo 의 기상청(KMA) 수치모델은 2026-03-31 부로 갱신이 중단**되어 사용하지 않습니다.
  기상청 예측은 단기예보로 반영하고, 한반도를 5km 로 덮는 일본기상청 MSM 을 추가했습니다.
- **Open-Meteo 무료 API 는 비상업적 이용만 허용**합니다(광고·유료 구독이 붙으면 안 됨). 출처 표기(CC BY 4.0)는 화면 하단에 있습니다.
- 이력 파일은 하루 약 0.2MB 씩 늘어납니다(연 70MB 안팎). 열차 지연 집계(`data/rail/`)는 하루 약 0.1MB 입니다.

## 한계

- 수치모델은 좁은 지역의 집중호우·돌풍을 낮게 예측하는 경향이 있습니다. ‘낮음’이 안전을 뜻하지 않습니다.
- 시청·군청 위치의 지점 예측값을 씁니다. 같은 시·군 안에서도 산지·해안·섬은 다를 수 있습니다.
- 한파특보의 “평년값보다 3℃ 이상 낮을 때” 조건, 폭염중대경보의 “35℃ 이상 2일 관측” 선행 조건은 반영하지 못합니다
  (그만큼 가능성이 높게 나올 수 있음).
- 기상청 단기예보의 1시간 강수량은 “50mm 이상”까지만 구분되어, 그 이상의 극한 강수는 50mm 로 계산됩니다.
- 건조·풍랑·황사·폭풍해일 특보는 계산하지 않고 발효 여부만 표시합니다.

## 2단계 (자료가 쌓인 뒤)

- 호우주의보는 과거 예보로 맞춘 기준을 이미 쓰고 있습니다(위 ‘계산 방법’ 4). 여름철 자료가 쌓이면 `tools/rain_study.py` 로 다시 맞춥니다.
- 다른 특보도 누적 이력으로 가능성 보정(예: 로지스틱 회귀로 모델 예측 → 실제 발효 확률). `data/history` 의 `x`(모델별 극값)·`h.r`(도달률)·`a`(실제 특보)를 그대로 쓸 수 있습니다.
- 가능성 ‘높음’ 시 푸시 알림, 지역 전국 확대.
- 구글 플레이 등록(TWA 래핑): `/.well-known/assetlinks.json` 을 **도메인 최상위**에 두어야 하므로,
  `<계정>.github.io/<저장소>/` 형태의 주소로는 안 되고 사용자 사이트 저장소(`<계정>.github.io`)나 자체 도메인이 필요합니다.
